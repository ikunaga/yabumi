## 問題がなかった主な点

- 新しい 11 表すべてで RLS が有効、anon への grant なし。sns_comments・attention_dismissals は列を絞った select だけ。auto_plans・auto_runs・post_target_approvals は select だけで、書くのは関数だけ。TikTok・YouTube の同意・アップロードの表とトークンは、利用者のロールに grant がない
- status・consented_at・approved_at・指紋・fail_streak・consumed_at・auto_run_id など、サーバーが決める値は列の grant に入っていないか、関数・トリガーで守っている
- security definer の関数はすべて search_path '' で、ACL は必要なロールだけ。auth.uid() が null なら断る
- 持ち主の違うものを指せない（save_auto_plan の材料、media_files の参照、TikTok・YouTube の表、close_attention ほか）
- post-videos は非公開。storage のポリシーは引換券を条件にした insert だけで、上書き・読み出しはできない
- ジョブ API 10 本は合言葉の完全一致（timingSafeEqual）。TikTok の Webhook は署名が必須で 5 分の窓、届いた内容は信じずに問い合わせ直す
- /tiktok-media のトークンは 32 バイトの乱数で、DB には SHA-256 だけ。1 時間で切れ、持ち主・配信先・画像を照合
- OAuth（TikTok・YouTube）は state を cookie で本人と結び、YouTube は PKCE も。戻り先は固定
- 費用のかかる AI・画像・YouTube の呼び出しは、どれも先に予約してから呼ぶ。上限はサーバーで固定
- 利用者のデータはタグで囲んで無害化し、system の指示は固定。通知とログに本文・トークンは出さない
- dangerouslySetInnerHTML なし、新しい NEXT_PUBLIC_* は Supabase の URL と公開キーだけ
