## 1. 背景・解決したい課題

オーナー自身が個人開発でアプリを開発しているが、以下の課題を抱えている。

| # | 課題 |
|---|---|
| P1 | アプリは作っているが、マーケティングがまったくできていない |
| P2 | SNS に疎く、どう運用していけばよいかわからない |
| P3 | 複数の SNS を運用するのが大変。アプリ開発に集中したいので、SNS 運用にあまり時間を割きたくない |
| P4 | 投稿するネタがあまりない |

## 2. 実現したいこと（ゴール）

- 上記の課題が解決される Web アプリがあり、SNS 運用を効率的に行える
- 同じ課題で困っている他の人（個人開発者など）にも提供できる

### F15 アカウント設計の中身

| セクション | 決めること | 「記入済み」とする条件 |
|---|---|---|
| 目的 | 何を広めたいか、いちばんの目標（ダウンロード / 課金 / 知ってもらう / その他） | 「何を広めたいか」か「いちばんの目標」のどちらか |
| 届けたい相手 | どんな人か（プロジェクトの「届けたい相手」と同じもの）、困りごと、どこで・いつ SNS を見ているか | 「どんな人か」 |
| 投稿の柱 | 投稿の種類と割合（最大 5 つ）、口調、やらないこと | 柱が 1 つ以上 |
| アカウントの持ち方 | 個人のアカウントを使うか、アプリ専用のアカウントを作るか、その理由 | どちらかを選んだ（「まだ決めていない」も可） |
| 名前とプロフィール | 表示名、ユーザー名（第一候補と予備 2〜3 個）、自己紹介文、リンク先。共通を土台に、SNS ごとに表示名・ユーザー名・自己紹介文・リンク先を変えられる（D26） | 表示名、ユーザー名、自己紹介文のどれか（共通か、どれかの SNS で） |
| 頻度と SNS ごとの役割 | 投稿の頻度、SNS ごとに何を出すか | 頻度 |
| 最初の 1 か月 | 1 か月後の目標、何を見て判断するか | 目標 |

- **主な入口は AI との会話**（D13）。AI が 1 問ずつ質問し、答えやすい選択肢を添え、答えにあわせて案を 2〜3 個（長所・短所、おすすめと理由つき）出す。利用者が選んだ案（または会話で直してもらった案）だけがそのセクションに保存される。AI の案には「AI の案」の印を付け、採用したセクションには「AI の案から」と出す
- 頻度と SNS ごとの役割のように素人が書けない項目は、AI が目的と投稿の柱から案を作る。SNS ごとの欄を並べて書かせることはしない
- フォームは「中身を確かめて手で直す」画面として残す。各セクションに「AI と考える」を置き、そこから会話を始められる。AI が使えない間（API キーがない、上限に達した）も、フォームで手で入力できる
- すべて任意入力で、セクションごとに保存でき、あとから直せる。各項目に素人向けの説明と記入例を添える
- **順番**: 上の表の順に並べ、まだ書いていない最初のセクションを開いた状態で始める。名前は「どういう投稿をしていくか」が決まらないと決めにくい（オーナーと実際に設計して詰まった点。2026-10-03）ので、投稿の柱 → 持ち方 → 名前の順にしている
- **名前とプロフィールの案内**:
  - ユーザー名（@ のあとの英数字）は後から変えにくく、表示名は変えやすい。「ユーザー名は慎重に、表示名は気軽に」と案内する
  - 6 つの SNS で同じ綴りが取れるかは、各 SNS にログインした状態で、ユーザー名を変える画面（新しく作るなら新規登録の画面）に入力して確かめる手順を案内する。ログインしていないと正しく判定できないため、空きを自動で調べる機能は作らない
  - Instagram とつないだ Threads のユーザー名は Instagram と同じになる、と Threads の欄に出す（2026 年から、Instagram から切り離した Threads と Instagram なしの Threads は別の名前にできる）
  - **SNS ごとに変える（D26、2026-10-12）**: 共通の欄の下に「SNS ごとに変える（任意）」。「頻度と SNS ごとの役割」に書いた SNS・つないだ SNS・すでに変えた SNS を 1 行ずつ（開くと欄が出る）並べ、ほかの SNS は折りたたむ。空の項目は共通を使う（欄に共通の値を薄く出す）。共通だけで済む人は、行が閉じたままで今までと同じ見た目
  - SNS ごとの決まり（ユーザー名の字数と使える文字、表示名と自己紹介文の字数、リンクの置き場所、変えられる回数）を行の中に出し、合わないところは欄の下と行の見出しで知らせる（保存は止めない。決まりは変わることがあるため）。値と出典は architecture.md の 4.8
  - つないだアカウントの実際のユーザー名が設計と違うときは「設計では @a、つないだのは @b」と出し、「設計を @b に合わせる」で設計の方を直して保存する
  - 行の中から、その SNS のプロフィール用の短縮リンク（F07）を作り、コピーし、リンク先に入れられる（短縮リンクの画面の「プロフィールに置くリンク」と同じもの）
  - AI と考える（F09）は、SNS ごとの役割が違うとき、その SNS 用の表示名と自己紹介文の案も出す。ユーザー名はそろえるのが基本で、取れないときや字数に合わないときだけ変える
- **設計の段階を「済み」とする基準**: 目的・届けたい相手・投稿の柱の 3 つが「記入済み」になったとき（投稿を書くのに欠かせない 3 つ）。済みになると、概要の「いまやること」が次の「SNS をつなぐ」に進む
- 設計は飛ばせる。「いまやること」の「あとで設計する」を押すと次の段階に進み、設計の画面はいつでも開ける（概要の「アカウント設計」とサイドバー）
- 投稿の作成画面で、投稿の柱と口調を見返せる
- AI の仕組み、モデルの選び方、費用の見積もりと上限は architecture.md の 4.9

### F04 ネタ作成サポートの中身

**作った範囲（2026-10-11）: 3 つの材料からネタを出す（D18）**

- 入口は「投稿をつくる」の見出しの横と、概要の「これからの投稿」の「AI とネタを出す」。画面は「投稿のネタを出す」
- 材料を 3 つから選ぶ。それぞれに、よいところと気をつけることを添えて、素人が選べるようにする
  - 最近の開発から（GitHub）: 読む期間（3 日〜1 か月、既定は 1 週間）を選ぶだけ。GitHub をつないでいなければ、つなぐ画面に案内する
  - 最近のできごとから: 「やったこと・変えたこと」「うまくいかなかったこと・迷ったこと」「使った人の声・自分で気づいたこと」の 3 つの質問（答えの例つき）のどれかに答える。GitHub を使わない人も使える
  - アカウント設計から: 入力なし。投稿の柱と「どんなアプリか」から、柱ごとに 1 つずつ、いつ出しても古くならないネタを出す。設計も紹介文も空なら、作り話になりやすいので先に書くよう案内する
- 材料の初期値は、前回の材料 → GitHub をつないでいれば最近の開発 → なければ最近のできごと
- 下書きを書く SNS（3 つまで）を選ぶ。AI がアカウント設計の投稿の柱・口調・やらないことに沿って、ネタを 3〜5 個出す
- 各ネタに、どの柱か、なぜこのネタがよいか（誰に何が伝わるか）、SNS ごとの下書き（文字数の目安つき）を付ける。材料がコミットなら、元にしたコミット（どんな変更かをやさしい言葉で）も付ける。素人が自分の話のどれが投稿になるかを判断しなくてよいようにする
- 材料だけでは「何に詰まって、どう直したか」「なぜそう作ったか」がわからないときは、AI が 2 つまで質問する（答えの例つき）。答えると出し直す。答えなくても使える
- 「このネタで下書きをつくる」で、投稿の下書き（日付なし）になり、投稿の画面で直して予約・送信できる
- AI のネタには「AI の案」の印を付ける。材料や答えにないこと（苦労話、数字）は書かせない。URL は入れない（X の費用が上がるため。リンクは利用者が足す）
- 読むのは GitHub App で選んだリポジトリだけ。秘密が入りがちなファイルは読まず、コミットの中身は保存しない（F16 と同じ決まり）
- ネタの会話は、プロジェクトごとに新しい 10 回分を残す（D18。どれも最後のやり取りから 1 年で消える。architecture.md の 4.14）
- 仕組みと費用（コミットから 1 回 $0.25 前後、ほかの材料は $0.1 前後）は architecture.md の 4.15

**まだの範囲**

- 短い投稿や下書きを、note・Substack の長文に広げる（architecture.md の 4.12「将来の案」）。いまのネタ出しは、自動で送る SNS（X、Threads、Instagram、Facebook、TikTok、YouTube）の短い文面だけを書く
- Issue からのネタ（GitHub App に Issues: Read を足す必要がある。architecture.md の 4.10）
- 過去の投稿の反応を見て、伸びた柱のネタを増やす（指標 F07 ができてから）
- 投稿の画面の中で、書きかけの下書きを AI に書き直してもらう（F11 で、指摘したところを直す案は出せるようになった。全体の書き直しはまだ）

### F11 AI っぽさチェックの中身（2026-10-11）

- 投稿の作成画面と投稿の画面に「送る前に AI に見てもらう」。手で書いた投稿も、AI のネタから作った投稿も同じように確かめる
- AI が送る文面を読み、「AI っぽい雑な投稿」になっていないかを指摘する。見るのは、書いた人しか知らない事実（本当か確かめてもらう）、決まり文句、誇張、ハッシュタグの付けすぎ、アカウント設計の口調とのずれ、「やらないこと」に当たるもの
- 素人前提: 指摘には、なぜよくないか（読む人にどう見えるか）と、直した案を添える。利用者は指摘ごとに「この直しを使う」か「そのままにする」を選べる。全体のひとこと（よいところを先に）も出す
- 送るのは止めない（知らせるだけ）。問題がなければ、よいところだけを伝える
- 結果は保存しない。費用は 1 回 約 $0.02 で、AI の月の上限に数える
- 仕組みと費用は architecture.md の 4.20

**まだの範囲**

- 送る直前（「今すぐ送る」「予約」を押したとき）に自動で確かめる（いまは利用者が押したときだけ。費用と待ち時間のため）
- 過去の投稿の反応（F07）から、その人の伸びた書き方に合わせた指摘

### F16 GitHub からアプリの紹介文を下書き

- 任意の最初の一歩として、概要の「いまやること」の上に「GitHub をつなぐ」を出す。飛ばしても先へ進める
- GitHub App として連携し、利用者がインストールのときに選んだリポジトリだけを読む。権限は中身とメタデータの読み取りだけ
- 画面では「説明」ではなく「アプリの紹介文（どんなアプリか）」と呼び、何に使われるか（アカウント設計の相談や投稿のネタの材料）を添える（2026-10-04、オーナーの「この『説明』ってなんの説明かわからん」を受けて）
- README が薄いリポジトリやモノレポでも中身がわかるよう、ファイル一覧から AI が読むファイルを選び（各アプリの README、設定、画面の文言、要件の資料など。15 件まで）、それを読んで書く（オーナーの「README しか読まないの？」を受けて）。秘密が入りがちなファイルは、一覧にも出さず読まない。読んだ中身は保存しない
- 紹介文にはわかったことだけを書き、わからないところは利用者への質問（答えの例つき、3 つまで）にする。答えると紹介文に反映される。「読み取れませんでした」や「このファイルは読んでいません」のような矢書の側の事情は見せない
- AI の下書きは「AI の案」として見せ、利用者が直して「この紹介文をプロジェクトに使う」を押したときだけ保存する。採用した紹介文は、アカウント設計の AI にも伝わる
- 仕組み、読むファイルの決まり、費用は architecture.md の 4.10

### F03・F14 投稿に画像を添える（2026-10-11 に作った範囲）

- 投稿の作成画面で画像を添える（10 枚まで）。並べ替え、外す、代わりの文（alt。画像が見えない人の読み上げや、表示されないときの説明）を書ける
- 画像は送る前にブラウザで JPEG に縮め、撮った場所などの情報（Exif）を消す。サーバーでも中身を確かめ、同じ情報を消す
- 送れる SNS: X（4 枚まで）、Threads（20 枚まで。2 枚以上はカルーセル）。Instagram（必須、10 枚まで）と Facebook は、つなぐときに同じ仕組みで送る。TikTok・YouTube（動画だけ）と note・Substack（手で投稿）には画像を送らない
- X は 2026-10-11 より前につないだアカウントだと、画像を送るのにつなぎ直しが要る（画面で案内する）。X は代わりの文 1 枚につき $0.005 かかる
- 画像は、送り終えて 30 日で矢書から消える（SNS には残る）。下書き・予約中は消えない。1 人 100MB まで
- 「画像をつくる」（2026-10-12）: テンプレートで文字のカード・図解・アプリの画面・note のヘッダーを作り、そのまま添える。AI が本文とアカウント設計から見出しや図解の項目の案を出す（1 回 2 円ほど。手でも書ける）。色は 6 つの組み合わせかアプリの色、書体は 4 つから選ぶ。縦横は送り先に合わせる（Instagram などは縦 4:5、X だけなら横 16:9）。画像の費用はかからない。スクリーンショットは AI に送らない（D25）
- AI で画像の背景を作る（F14 の段取り ②）と、動画の添付は、まだ作っていない
- 仕組み・上限・保存期間は architecture.md の 4.18

### F07・F08 指標と改善分析（2026-10-11 に設計。コードはまだ）

- 「数字」の画面では、アカウント設計の「最初の 1 か月」の目標に合わせた数字を 1〜3 個だけ先頭に出す（知ってもらう → 閲覧数とフォロワー、ダウンロード → ストアへのクリックとダウンロード、課金 → 課金）。用語には解説を添え、細かい数字は折りたたむ
- SNS の数字: Threads・Instagram・Facebook は無料（それぞれ数字の権限を足して審査が要る）。X は読むたびに有料（1 人 月 約 $0.64。読むかはオーナーの判断）。note・Substack は手で入れる
- ストアページ到達: 矢書が発行する短縮リンク（go.yabumi.app）で、SNS ごと・投稿ごとにクリックを数える。X は本文に URL があると投稿の費用が上がるので、プロフィールのリンクで数える
- ダウンロードと課金: App Store Connect（Sales and Reports の API キー）、Google Play（利用者ごとのサービスアカウントを Play Console に招待）、RevenueCat（読み取りの鍵）から日ごとに取り込む。どの投稿から来たかまではわからないので、日ごとに投稿・クリックと並べて見せる
- 改善分析（F08）の入口: AI が先週の数字から「よかった投稿・次に試すこと」を出す（AI の案として。採用したら設計に反映）
- 仕組み・費用・段取り・オーナーが決めることは architecture.md の 4.22

LinkedIn、Bluesky は現時点では対象外。

## 5. 想定ユーザー

1. **一次**: オーナー自身（個人開発者、マーケティング・SNS に不慣れ、運用に時間をかけたくない）
2. **二次**: 同じ課題を持つ他の個人開発者・小規模開発者

まずオーナー専用として動かし、後からマルチユーザー化して二次ユーザーへ提供する（D2）。
ただし最初から複数ユーザーを想定したデータ構造にしておき、後の作り直しを避ける。

## 6. 非機能的な要望（会話から読み取れるもの）

- 運用にかかる時間を最小化する（ツールを開くだけで次にやることがわかる、入力が少ない）
- 素人でも使えて、使うほど知識がつく（専門用語を前提にしない UI、解説が添えられている）
- AI 生成物がそのまま出ていかない（人の投稿として自然な品質を保つ）
- 運用コストを低く抑える。目安は月額 3,000 円程度（D4, D8）。他の人に出したあとの費用と料金プランは D24

## 9. 既知の制約（参考）

他者提供を前提にすると、各 SNS の API 審査・料金が主な制約になる。審査の中身と手順は [review/](review/README.md)、利用規約とプライバシーポリシーは [legal.md](legal.md)（2026-10-11）。

- 他の人に提供するには、利用規約とプライバシーポリシーを、登録の前に読める形で出す（X・Meta・TikTok・Google のどれもが求める）。/terms と /privacy に下書きがある
- YouTube（Google の確認）と TikTok（URL の所有確認）は、独自ドメインが要る（`vercel.app` は自分のドメインとして証明できない）

- X: 2026 年 2 月から無料枠はなく、使った分だけ払う方式（投稿 1 本 $0.015、URL があると $0.20、閲覧数などの取得も 1 件ごとに有料）。D16
- Instagram / Facebook / Threads: Meta のアプリ審査が必要。Instagram はビジネス/クリエイターアカウント必須でテキストのみ投稿は不可
- TikTok: 審査通過前は非公開投稿のみ
- YouTube: 1 日の API クォータが小さく、動画投稿は 1 日数本が上限
- Bluesky: 審査なし・無料
- 広告配信: X Ads、Meta 広告、TikTok 広告、Google 広告（YouTube）はそれぞれ別の広告 API と審査があり、広告費の支払いは各社のアカウントで行う
- コンバージョン計測: ストアページ到達は自前の短縮リンクで計測できる。ダウンロードと課金は SNS 側からは取れないため、ストアや課金基盤の API から取り込む必要がある
- コンバージョン計測の取得元（D9）: ダウンロード数は App Store Connect API と Google Play Console のレポートから取得する。どちらも日次集計で、リアルタイムではない。課金は RevenueCat などの課金基盤を使っていればその API から取れる。各ストアの API から直接取ることもできる
