## 1. 進め方の考え方

- まず「投稿が楽になる」ところまでを最短で作り、自分で使い始める。使いながら次の機能の優先度を決める
- 指標は投稿が動いてから作る。指標の画面は実データがないと設計しにくいため
- SNS 各社の審査は時間がかかるので、開発と並行して早めに申請する

- Claude Design の 1b「藍と朱・送り状の帳面」を実装。トークン、共通部品、今ある画面（トップ、登録・ログイン、プロジェクト一覧・作成・詳細・編集、用語解説）

### フェーズ 1 の前半（2026-10-03）

SNS との連携がなくても作れる部分を先に作った。

- テーブル: SNS アカウント、トークン（画面側からは読めない）、プロジェクトとの紐づけ、投稿、SNS ごとの配信先
- SNS ごとのルール: 文字数（X は全角換算で 140 字）、画像・動画が必要かの判定
- 投稿をつくる画面: 下書き、送り先の選択、SNS ごとの文面調整とプレビュー、送る日時、下書き保存、削除
- カレンダー: 週の表示（PC は 7 列、スマホは日付ごとの縦リスト）、空いている日から投稿を足す、日付のない下書きの一覧
- 概要の「これからの投稿」
- 日時はすべて日本時間で扱う（海外の利用者に対応するときは利用者ごとのタイムゾーンを持つ）

まだできないこと:

- 予約: SNS をつなぐまでは押せない（下書きとして日付つきで保存し、カレンダーに予定として出せる）
- 実際の送信と、予約時刻に送るジョブ
- 画像・動画の添付（フェーズ 5）

### フェーズ 1 の後半: Threads の接続（2026-10-03）

- Meta アプリ「Yabumi Dev」（Threads 専用、開発モード）をオーナーが作成。Threads Tester に自分のアカウントを登録
- 開発サーバーを https で起動するようにした（Threads のコールバック URL が https 必須のため。https://localhost:3100）
- 概要に「つないだ SNS」を追加。Threads の「つなぐ」→ Threads の認可画面 → 長期トークン（60 日）に交換 → 暗号化して保存 → プロジェクトにつなぐ
- state による CSRF 対策（cookie と照合し、始めた利用者と同じかも確かめる）
- Meta からのアンインストール通知（トークンを消してアカウントを「解除済み」に）と、データ削除の通知（アカウントごと削除し、確認 URL とコードを返す）
- 「いまやること」の「つなぐ」「投稿をつくる」を押せるようにした。プロジェクト一覧の「つないだ SNS」に実際の値を出す

まだできないこと（この時点）: 送信、予約ジョブ、トークンの自動延長。下の「Threads への送信と予約ジョブ」で対応

### フェーズ 1 の後半: Threads への送信と予約ジョブ（2026-10-03）

- SNS アダプターの形を決め、Threads の部品を作った（文章の投稿、SNS 上での取り消し、トークンの延長）
- 投稿の画面に「今すぐ送る」を追加し、「予約」も押せるようにした（つないでいて、送信の部品がある SNS だけ）
- 予約時刻に送るジョブ（pg_cron から毎分）と、トークンを延長するジョブ（毎日 3:00）。ローカルでは pnpm jobs:bridge で動く
- 二重送信の防止（取り出しと状態の書き換えを 1 つの文で行う。送信の状態は利用者が書き換えられない）と、やり直し（最大 3 回）
- 投稿の画面に「送信の結果」（Threads で見る、Threads から取り消す、失敗の理由と「要確認」）。概要に「要確認　送れなかった投稿」

まだできないこと:

- 本番環境（Supabase・Vercel）。本番の Vault と環境変数の設定は architecture.md の 4.7
- Instagram・Facebook・TikTok・YouTube への送信（X は 2026-10-11 に追加）
- 画像・動画の添付（フェーズ 5）

### アカウント設計のステップ（2026-10-03、D12）

### アカウント設計を AI と進める形に（2026-10-03、D13）

- オーナーの指示で、F09（AI 壁打ち）の一部を前倒しした
- 設計の主な入口を「AI と考える」（会話）にした。AI が 1 問ずつ質問し、選択肢を添え、案を 2〜3 個（長所・短所、おすすめと理由つき）出す。「この案にする」で、そのセクションに保存される
- フォームは「中身を確かめて手で直す」画面として残し、各セクションに「AI と考える」を置いた。AI の案から採用したセクションには「AI の案から」と出す
- Claude API（Claude Opus 5.5）を使う。費用は設計 1 回あたり約 $1。利用者ごと・全体の月の上限と、1 日の回数の上限を入れた（architecture.md の 4.9）
- API キーがない間は「AI と考える」を押せない状態で「準備中」と出す

### note と Substack を手で投稿する SNS として追加（2026-10-04、D15）

- どちらも公式の投稿 API がないことを確かめ、「手で投稿する SNS」という種類を作った
- 投稿をつくる: note と Substack を送り先に選べる。タイトルと長文の本文。予約は「この日に投稿する予定」
- 手で投稿する流れ: 本文をコピー → 投稿の画面を開く → 手で投稿 →「投稿した」（URL は任意）で記録。時刻が来たら概要の「手で投稿する番です」で知らせる。予約ジョブは拾わない
- 概要の「つないだ SNS」に「手で投稿」として出し、プロフィールの URL を登録できる
- アカウント設計の「SNS ごとの役割」と AI の壁打ちに、note と Substack の性格を加えた（目的に合うときだけ提案）

### X に自動で投稿する（2026-10-11、D16）

- X の API の料金を調べた（T1）。無料枠はなく、投稿 1 本 $0.015、URL があると $0.20。オーナーの判断で、従量課金で自動で送り、月 $3 を上限にした
- X をつなぐ（OAuth 2.0 + PKCE）、送る・予約・取り消す。使い捨てのリフレッシュトークンは、DB で権利を取った 1 か所だけが取り直す
- 送る前に費用を記録し、月の上限を超えたら送らずに「要確認」。送れなかった X は、本文入りの投稿画面を開いて手で投稿し、記録できる
- 作成画面で、URL があるときの費用の差と代わりの案を出す。概要に今月の X の費用と上限
- X の文字数の数え方を直した（https:// のない URL、組み合わせた絵文字）
- オーナーの作業: X の開発者登録・クレジットの購入・Spending limit・アプリの作成（README の「X」）

### 最近のコミットから投稿のネタを出す（2026-10-11、F04 の一部）

- 「最近の開発からネタを出す」の画面（/projects/[id]/ideas）。入口は「投稿をつくる」の見出しの横（「AI に案を出してもらう（準備中）」を置き換えた）と、概要の「これからの投稿」
- GitHub App で、つないだリポジトリの期間のコミット（3 日〜1 か月）を読む。権限は足していない（Contents: Read で読める）。秘密の除外と伏せ字は紹介文の下書きと同じものを通し、原文は保存しない
- AI（Claude Opus 5.5）が、投稿の柱・口調・やらないことに沿ってネタを 3〜5 個と、SNS ごとの下書きを出す。わからないところは 2 つまで質問し、答えると出し直す
- ネタを選ぶと投稿の下書きになる（save_post）
- ネタは AI の会話（ai_threads の purpose に post_ideas を追加）に置き、プロジェクトごとに新しい 10 回分だけ残す
- 費用は 1 回 $0.25 前後（drift で試した実績 $0.23）、出し直し $0.12。既存の AI の上限に数える
- 用語集に「Build in Public」を追加

まだできないこと（requirements.md の「F04 の中身」）: note・Substack の長文に広げる、GitHub を使わない人向けのネタ出し（下の節で作った）、Issue から、反応を見て柱を調整する

### GitHub を使わない人のネタ出し（2026-10-11、F04 の一部、D18）

- 「投稿のネタを出す」で、材料を「最近の開発（GitHub）」「最近のできごと（3 つの質問のどれかに答える）」「アカウント設計（入力なし、柱ごと）」から選べるようにした。それぞれによいところと気をつけることを添える
- GitHub をつないでいない人は「最近のできごと」から始まる。つないでいる人も 3 つとも使える
- 利用者にしか書けないところは、AI が【作品名】のように【】で示す。【】が残った投稿は予約・送信できない
- 入口の文言を「AI とネタを出す」にした（「投稿をつくる」の見出しの横、概要の「これからの投稿」）
- 費用は news・plan が 1 回 $0.07（実績）

### 他の人に提供するための準備: 規約・審査・GitHub App（2026-10-11、D17）

- 利用規約（/terms）とプライバシーポリシー（/privacy）の下書き。ログインなしで開け、トップ・ログイン・登録の画面からリンクし、登録の画面に同意の一文を出す。預かるもの・送り先（Anthropic、Meta、X、GitHub、Supabase、Vercel、Resend、Cloudflare）・保存期間・消し方は architecture.md の 4.14 に合わせた。Anthropic の扱い（既定で学習に使わない、30 日以内に消す、保存は米国）は公式の資料で確かめた（docs/legal.md）
- 運営者・問い合わせ先・施行日・管轄・年齢、保存期間（1 年・13 か月）は「確認中」。決まるまで、ページの先頭に「確認中の下書き」と出す（src/lib/legal/info.ts）
- SNS 各社の審査の準備（docs/review/）: Meta（ビジネス認証、権限ごとの説明文と録画の流れ、Tech Provider 認証、データ削除の URL）、X（審査は不要。規約上の表示と同意）、TikTok・YouTube（監査、独自ドメインが要ること、投稿の画面の決まり）
- GitHub App を Any account にする準備: 組織や共同作業者のインストールで、本人が読めない非公開リポジトリまで読めてしまう穴を見つけて直した（本人が読めるリポジトリを記録し、一覧・つなぐ・読む直前で確かめる。7 日ごとに確かめ直す。architecture.md の 4.10）。公開・名前・ロゴの手順を deploy.md の 10 に書いた

まだできないこと（オーナーの判断・作業待ち）:

- 規約とポリシーの「確認中」を埋める（docs/legal.md の L1〜L11）
- 独自ドメインを取るか（YouTube の確認には必須。docs/review/README.md の R1）、Meta のビジネス認証の名義（R2）
- X で消された投稿の記録を「最新に保つ」扱い（docs/review/x.md の「残り」）
